- **P1**: `src/Antigravity.Core/Commands/AutoFoundationCommand.cs:167` - Type creation reports success even when dimensions are not applied
  TryGetOrCreateFoundationType ignores the Boolean results from both Parameter.Set calls and unconditionally returns true. Revit parameters can reject a value without the adapter detecting it, so CAD dimensions that violate family constraints may produce and place a foundation with the duplicated base dimensions while the command reports success. Require both parameters to exist and both Set operations to succeed, then verify the resulting values or return false/throw so the transaction cannot commit incorrectly sized structural foundations.
- **P1**: `src/Antigravity.Core/Models/FoundationData.cs:5` - Auto-placement behavior is not implemented
  The change only introduces a passive data container for coordinates, rotation, and dimensions. It contains no CAD-data conversion, foundation placement logic, or callable behavior that could satisfy AC-03 (“Auto place foundation from CAD”). As the entire reviewed implementation consists of this model, the requested feature is absent.
- **P1**: `src/Antigravity.Core/Services/CadParserService.cs:68` - Unrelated lines can split a valid foundation across elevation groups
  Each group is anchored to the lowest line's Z via groupStartZ. Consequently, membership depends on unrelated geometry encountered earlier. For example, an unrelated line at Z=0.000 causes foundation edges at Z=0.009 to join its group, while the remaining edges at Z=0.011 start another group, even though the foundation edges differ by only 0.002 and would all group together without the unrelated line. The polygon is then split and no foundation is extracted. Group elevation after identifying spatially connected line sets, or otherwise ensure unrelated lines cannot change whether a connected candidate falls within the elevation tolerance.
- **P2**: `src/Antigravity.Core/Services/FoundationPlacementOrchestrator.cs:19` - Null input crashes the placement operation
  PlaceFoundations enumerates foundationsData without validating it. Passing null therefore raises a NullReferenceException instead of a clear ArgumentNullException. This public orchestration boundary already validates its adapter dependency and should likewise guard the input collection. Add an explicit null check and a focused test.
